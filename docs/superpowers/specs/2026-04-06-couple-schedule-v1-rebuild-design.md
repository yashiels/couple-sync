## 1. Purpose

Build a mobile app (iOS + Android) that helps long-distance couples find mutual free time. Two people pair up, define their busy time via Google Calendar sync and manual blocks, and a server-side engine computes when they're both free. Results are ranked by quality and pushed to both partners.

The core question this app answers: "When are you free?" — automatically, across timezones.

### Why These Choices

- **Flutter**: Single codebase for iOS + Android. Team familiarity from prior Nexion Tech projects.
- **Firebase**: Real-time sync (Firestore) is critical for couples seeing each other's updates instantly. Free tier covers development and early users. Cloud Functions v2 for server-side overlap computation.
- **Riverpod**: Type-safe, testable state management. No context dependency.
- **go_router**: Declarative routing with redirect guards (auth state, onboarding flow).
- **Google Calendar freebusy API**: Returns busy/free intervals without exposing event titles. Privacy-first.

## 3. Architecture

```
+------------------+     +------------------+
|  Partner A App   |     |  Partner B App   |
|  (Flutter)       |     |  (Flutter)       |
+--------+---------+     +--------+---------+
         |                         |
         |    Cloud Firestore      |
         |    (real-time sync)     |
         +----------+--------------+
                    |
         +----------+--------------+
         |   Cloud Functions v2    |
         |   - onBlockWrite        |
         |   - onOverlapWrite      |
         |   - onInviteCreate      |
         |   - cleanupInvites      |
         +----------+--------------+
                    |
              Google Calendar
              API v3 (freebusy)
```

### Data Flow

1. User signs in → Firebase Auth creates session → app fetches/creates user doc in Firestore
2. User pairs with partner → invite code redeemed → couple doc created → both user docs updated with coupleId
3. User syncs Google Calendar → freebusy data written as TimeBlocks to Firestore
4. User adds manual blocks → written to Firestore
5. Any block write triggers `onBlockWrite` Cloud Function → computes overlap → writes to overlaps collection
6. Overlap write triggers `onOverlapWrite` → sends FCM push to both partners
7. Both apps receive real-time Firestore updates → UI refreshes

## 5. Cloud Functions (6 total)

### 5.1 onBlockWrite

**Trigger:** Firestore onCreate/onUpdate/onDelete on `timeblocks/{coupleId}/blocks/{blockId}`

**Debouncing:** Calendar sync deletes and rewrites many blocks at once, which would trigger this function N times. To handle this: the function checks `blockHashA`/`blockHashB` on the existing overlap doc before writing. If the hashes haven't changed (i.e., another invocation already computed with the same block set), it skips. Additionally, the function uses a 2-second delay (via Cloud Tasks or a simple setTimeout) to let batch writes settle before querying.

**Logic:**
1. Wait 2 seconds for batch writes to settle
2. Read couple doc → get both user UIDs and timezones
2. Query all blocks for this coupleId (14-day horizon from now)
3. Expand recurrence rules (RFC 5545) into concrete time instances within the 14-day window
4. Per partner: build sorted busy timeline, merge overlapping intervals
5. Per partner: invert busy timeline to get free intervals
6. Intersect both partners' free intervals
7. Clip to waking hours: 7am–11pm in each partner's local timezone
8. Filter out windows shorter than 30 minutes
9. Score each window (see scoring algorithm)
10. Sort by score descending, take top 20
11. Compute block hashes for change detection
12. Write result to `overlaps/{coupleId}/windows/latest`

**Scoring algorithm:**
```
base = log2(durationMinutes + 1) * 10
eveningBonus = bothInEvening(17:00-22:00 local) ? +30 : oneInEvening ? +10 : 0
weekendBonus = (Saturday or Sunday for both) ? +15 : 0
timeDecay = -daysFromNow * 0.5
score = round(base + eveningBonus + weekendBonus + timeDecay, 1)
```

### 5.2 onOverlapWrite

**Trigger:** Firestore onWrite on `overlaps/{coupleId}/windows/latest`

**Logic:**
1. If no windows or content unchanged (compare block hashes), skip
2. Read FCM tokens for both partners from their user docs
3. Send push notification: "New free time found! [date] at [time] for [duration]"
4. Remove any stale/invalid FCM tokens discovered during send

### 5.3 onInviteCreate

**Trigger:** Firestore onCreate on `invites/{code}`

**Logic:**
1. Generate a deep link URL using the app's custom URL scheme (e.g., `coupleschedule://invite/{code}`) and an associated HTTPS fallback (e.g., `https://coupleschedule.app/invite/{code}`) for App Links (Android) and Universal Links (iOS)
2. Write the deep link URL back to the invite doc

**Note:** Firebase Dynamic Links was deprecated in August 2025. Deep linking is handled natively via App Links (Android `assetlinks.json`) and Universal Links (iOS `apple-app-site-association`). The HTTPS fallback URL can be hosted as a simple redirect on Firebase Hosting (free tier).

### 5.5 redeemInvite (callable)

**Trigger:** HTTPS callable function, invoked by client when partner B enters an invite code

**Logic:**
1. Validate caller is authenticated
2. Validate invite exists, status is "pending", and not expired
3. Validate caller is not the invite creator (can't pair with yourself)
4. Validate neither user is already paired (both coupleId must be null)
5. Create couple doc with both UIDs, status "active"
6. Update both user docs with coupleId (batch write via admin SDK)
7. Update invite status to "accepted", set coupleId
8. Return success with coupleId

### 5.6 cleanupExpiredInvites

**Trigger:** Cloud Scheduler, daily at 03:00 UTC

**Logic:**
1. Query invites where `expiresAt < now` and `status == "pending"`
2. Batch update status to "expired"

## 6. Google Calendar Integration

- OAuth2 via `google_sign_in` Flutter package with `calendar.readonly` scope
- Uses **freebusy API only** — no event titles are fetched or stored (privacy-first)
- Syncs primary calendar only, 14-day lookahead
- Synced intervals are written as TimeBlocks with `source: "google"`
- On sync: delete all existing google-sourced blocks for this user → write fresh batch → this triggers onBlockWrite
- Auto-sync on app launch if last sync was more than 1 hour ago
- Manual sync available via pull-to-refresh and settings

## 7. Auth & Session Flow

1. Firebase Auth with Google and Apple providers (no email/password, no anonymous)
2. On sign-in success: fetch user doc from Firestore. If none exists, create one with auth provider data.
3. Hydrate app state (current user, couple, blocks) before rendering any routes
4. go_router redirect guards:
   - Not authenticated → auth screen
   - No timezone set → timezone setup screen
   - No coupleId → pairing screen
   - Has couple → home screen
5. On sign-out: clear all Riverpod state → redirect to auth screen

## 8. Screens (10 total)

### 8.1 Auth Screen
Google Sign-In button + Apple Sign-In button. Creates/fetches user doc on success.

### 8.2 Timezone Setup
Auto-detect device timezone as default. Searchable IANA timezone list for override. Saves to user doc. One-time during onboarding, editable in settings.

### 8.3 Routine Setup Wizard
Step-through flow: sleep → work/study → commute. Each step creates recurring TimeBlocks with appropriate category and RRULE. Skip option per step. All times entered in user's local timezone, stored as UTC.

### 8.4 Pairing Screen
Tab 1 (Share): generate 6-char invite code, copy button, share deep link. Tab 2 (Enter): text field to enter partner's code, validate, redeem. Listens to user doc — auto-navigates to home when coupleId is set.

### 8.5 Home Screen
Timezone clocks (yours + partner's, live). Next free window card with countdown. Upcoming 5 windows list. Quick actions: add block, sync calendar, view all windows. Pull-to-refresh.

### 8.6 Calendar Week View
7-day scrollable, pageable by week. Color-coded: your blocks, partner's blocks, overlap highlights. Tap block for details. Tap overlap for score. FAB to add new block.

### 8.7 Overlap / Free Windows Screen
All computed windows (up to 20). Filter by minimum duration (any, 30m, 1h, 2h). Each card: date, time range (your tz + partner's tz), duration, score. Default sort by score.

### 8.8 Block Management Screen
List all your blocks (manual + synced). Filter by source and category. Edit/delete manual blocks. Synced blocks are read-only.

### 8.9 Block Form Screen
Fields: title, type (busy/free/tentative), category, date+time pickers (local tz), recurrence (none/daily/weekly with day picker/monthly), visibility (both partners/only me). Validation: title required, end must be after start.

### 8.10 Settings Screen
Calendar: connect/disconnect Google, last sync time, manual sync. Timezone: view/change. Routine: re-run setup wizard. Notifications: toggle new-window alerts. Couple: partner info, unpair with confirmation dialog. Account: sign out.

## 9. Firestore Security Rules

```
users/{uid}: 
  - read: auth.uid == uid OR (caller is partner via coupleId lookup)
  - write: auth.uid == uid (all fields)
  - no exceptions — coupleId is written by Cloud Functions only

couples/{coupleId}:
  - read: auth.uid == resource.data.userAUid OR auth.uid == resource.data.userBUid
  - write: Cloud Functions only (admin SDK)

invites/{code}:
  - read: any authenticated user
  - create: any authenticated user
  - update: creator (createdByUid) or redeemer (status field only)

timeblocks/{coupleId}/blocks/{blockId}:
  - read/write: auth.uid is member of parent couple doc (requires get() on couples/{coupleId}, costs 1 read)

overlaps/{coupleId}/windows/latest:
  - read: auth.uid is member of parent couple doc
  - write: Cloud Functions only (admin SDK)
```

**Note on pairing atomicity:** When partner B redeems an invite, the client calls a `redeemInvite` Cloud Function (not a direct Firestore write). The function validates the invite, creates the couple doc, and updates both user docs' `coupleId` in a single batch — all via admin SDK. This avoids the security hole of allowing any auth user to write another user's coupleId.

## 10. Firestore Composite Indexes

These queries require composite indexes (defined in `firestore.indexes.json`):

1. **timeblocks/{coupleId}/blocks** — query by `userId` + `startUtc` (ascending) for per-partner block retrieval in date order
2. **timeblocks/{coupleId}/blocks** — query by `source` + `userId` for calendar sync delete-and-replace (delete all google blocks for a user)
3. **invites** — query by `status` + `expiresAt` for cleanup job

## 11. Partner Data Flow

When a user is paired, the app needs to display partner info (name, timezone, photo):

1. On app launch (after auth hydration), if user has `coupleId`, read the couple doc
2. From couple doc, determine partner UID (the one that isn't the current user)
3. Read partner's user doc (allowed by security rules — partner read via coupleId match)
4. Store partner info in a Riverpod provider (`partnerProvider`)
5. Listen to partner's user doc for real-time updates (timezone changes, etc.)

This provider powers: home screen partner clock, overlap display in partner's timezone, settings partner info section.

## 12. Timezone Handling

- All timestamps stored in UTC (milliseconds since epoch) in Firestore
- Each user doc stores their IANA timezone string
- Each TimeBlock stores the timezone it was created in
- Display layer converts UTC to the viewing user's local timezone
- Home screen shows both partners' current local times
- Overlap engine uses both timezones for waking-hours clipping (7am-11pm local)
- Cloud Functions: Luxon for all timezone math
- Flutter: `timezone` package for all timezone math

## 13. Notification Strategy

- FCM token registered on app launch and stored in user doc's `fcmTokens` array
- Multiple tokens per user supported (multiple devices)
- Only one notification type in v1: "New free time found"
- Triggered by onOverlapWrite Cloud Function, not client-side
- Notification payload includes: window date, time in recipient's timezone, duration
- Stale tokens pruned on send failure
- User can toggle notifications on/off in settings (client-side suppression via local flag)

## 14. Offline Behavior

- Custom blocks can be created offline (Firestore offline persistence)
- Blocks sync to server when connection is restored, triggering overlap recomputation
- Google Calendar sync requires connectivity (OAuth + API call)
- Overlap results are cached locally via Firestore offline cache
- App is fully usable for viewing cached data while offline

## 15. Privacy Model

- **Default:** Busy/free only. No event titles from Google Calendar are fetched (freebusy API).
- **Manual blocks:** Title is visible to partner if visibility is "bothPartners". "onlyMe" blocks appear as unnamed busy time to partner. **Important:** This privacy is enforced at the query/display layer, not via Firestore security rules (both partners need read access to all blocks for the overlap engine). The client queries only `bothPartners` blocks for partner display. A determined user with Firestore API access could read "onlyMe" blocks — this is an accepted trade-off for v1. True server-side enforcement would require splitting blocks into separate subcollections per visibility level, adding complexity.
- **No calendar data stored on server beyond busy intervals.** Google Calendar freebusy responses are transformed into TimeBlocks (start/end/busy) and the raw response is discarded.

## 18. Out of Scope (v1)

- AI activity suggestions (Gemini)
- Pattern detection (recurring windows)
- Apple Calendar / Microsoft Outlook integration
- Web platform
- Relationship stats / analytics dashboard
- Home screen widgets (iOS/Android)
- Group mode (friends/family)
- In-app chat
- Calendar event creation from free windows
- Shared notes on windows

## 19. Success Criteria

The v1 is complete when:
1. Two users can sign in (Google or Apple) on separate devices
2. Both set their timezone and complete routine setup
3. They pair via invite code
4. Google Calendar sync pulls freebusy data as blocks
5. Manual blocks can be created (one-off and recurring)
6. Overlap engine computes mutual free windows within 5 seconds of a block change
7. Both partners see the same overlap results in their respective timezones
8. Push notification fires when new free windows are found
9. All 10 screens are functional and navigable
10. App works on both iOS and Android
